## 概述

微服务架构是当前最主流的软件架构风格之一。本文将从单体应用的痛点出发，逐步介绍微服务架构的核心概念和最佳实践。

## 为什么需要微服务

### 单体应用的痛点

传统的单体应用将所有功能打包在一个可部署单元中，随着业务增长会面临以下问题：

- **代码耦合严重**：修改一个功能可能影响整个系统
- **扩展困难**：只能整体扩容，无法针对热点模块
- **部署风险高**：每次部署都是全量更新
- **技术栈锁定**：难以引入新技术

### 微服务的优势

微服务将应用拆分为一组小型、独立部署的服务，每个服务：

- 围绕业务能力构建
- 独立部署和扩展
- 拥有自己的数据存储
- 通过轻量级协议通信

## 核心设计原则

### 单一职责原则

每个微服务只负责一个明确的业务领域：

```
用户服务    → 用户注册、登录、权限管理
订单服务    → 订单创建、状态管理、历史查询
商品服务    → 商品信息管理、库存管理
支付服务    → 支付处理、退款、对账
通知服务    → 邮件、短信、推送通知
```

### 服务间通信

微服务之间常用的通信方式：

**同步通信（REST/gRPC）**

```typescript
// 使用REST API调用订单服务
async function createOrder(userId: string, items: CartItem[]) {
  // 调用商品服务检查库存
  const stockCheck = await fetch(`${PRODUCT_SERVICE_URL}/api/stock/check`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ items }),
  })

  if (!stockCheck.ok) {
    throw new Error('库存不足')
  }

  // 创建订单
  const order = await db.orders.create({
    userId,
    items,
    status: 'pending',
  })

  return order
}
```

**异步通信（消息队列）**

```typescript
// 使用RabbitMQ发送订单事件
import amqp from 'amqplib'

async function publishOrderCreated(order: Order) {
  const connection = await amqp.connect(RABBITMQ_URL)
  const channel = await connection.createChannel()

  await channel.assertQueue('order-events')
  channel.sendToQueue(
    'order-events',
    Buffer.from(JSON.stringify({
      type: 'ORDER_CREATED',
      orderId: order.id,
      userId: order.userId,
      totalAmount: order.totalAmount,
    }))
  )

  await channel.close()
  await connection.close()
}
```

## 服务注册与发现

在微服务架构中，服务实例的地址是动态变化的，需要服务注册与发现机制：

```typescript
// 服务注册
class ServiceRegistry {
  private services: Map<string, ServiceInstance[]> = new Map()

  register(serviceName: string, instance: ServiceInstance) {
    const instances = this.services.get(serviceName) || []
    instances.push(instance)
    this.services.set(serviceName, instances)
    console.log(`服务注册: ${serviceName} -> ${instance.host}:${instance.port}`)
  }

  discover(serviceName: string): ServiceInstance | null {
    const instances = this.services.get(serviceName)
    if (!instances || instances.length === 0) return null
    // 简单的轮询负载均衡
    const index = Math.floor(Math.random() * instances.length)
    return instances[index]
  }

  deregister(serviceName: string, instance: ServiceInstance) {
    const instances = this.services.get(serviceName) || []
    this.services.set(
      serviceName,
      instances.filter(i => i.host !== instance.host || i.port !== instance.port)
    )
  }
}
```

## 熔断与限流

### 熔断器模式

防止故障在微服务间级联传播：

```typescript
class CircuitBreaker {
  private state: 'CLOSED' | 'OPEN' | 'HALF_OPEN' = 'CLOSED'
  private failureCount = 0
  private readonly threshold: number
  private readonly timeout: number

  constructor(threshold = 5, timeout = 30000) {
    this.threshold = threshold
    this.timeout = timeout
  }

  async call(fn: () => Promise<any>): Promise<any> {
    if (this.state === 'OPEN') {
      throw new Error('熔断器已开启，请求被拒绝')
    }

    try {
      const result = await fn()
      this.onSuccess()
      return result
    } catch (error) {
      this.onFailure()
      throw error
    }
  }

  private onSuccess() {
    this.failureCount = 0
    this.state = 'CLOSED'
  }

  private onFailure() {
    this.failureCount++
    if (this.failureCount >= this.threshold) {
      this.state = 'OPEN'
      setTimeout(() => { this.state = 'HALF_OPEN' }, this.timeout)
    }
  }
}
```

## 可观测性

微服务架构需要完善的可观测性方案：

- **日志（Logging）**：集中式日志收集（ELK Stack）
- **指标（Metrics）**：系统监控（Prometheus + Grafana）
- **追踪（Tracing）**：分布式链路追踪（Jaeger/Zipkin）

## 总结

微服务架构不是银弹，它带来了分布式系统固有的复杂性。在采用微服务之前，需要认真评估团队规模、业务复杂度和技术能力。一般来说：

- 小型团队、初期项目 → 单体架构
- 中型团队、业务增长 → 模块化单体
- 大型团队、复杂业务 → 微服务架构

选择合适的架构，才是最好的架构。
